# Ludo Atlas · AI 工作流 · 游戏开发需要的 Skill

> 本页回答一个问题：让智能体真正参与游戏开发，需要准备哪些 Skill，怎么准备。
> 先给一句结论：Skill 不是玄学提示词，而是「说明 + 脚本 + 检查」三件套，写得能复用、能审查、能交接。
> 时点 2026 年 10 月；Skill 与工具生态变化快，机制细节以各家官方文档为准（入口见《资源大全》§2.9）。

---

## 1. 先把三个词分清

| 词 | 是什么 | 类比 |
| --- | --- | --- |
| Skill（技能包） | 一类活「怎么干」的可复用说明：触发条件、步骤、脚本、验收 | 岗位操作手册 |
| MCP（工具接口） | 智能体连接外部工具（编辑器、Blender、浏览器）的协议层 | 手和眼 |
| 规则文件 | AGENTS.md 这类项目级约定：命令、规范、禁区 | 厂规 |

一句话关系：MCP 给它手，Skill 教它怎么用这双手干某类活，规则文件划定什么不许干。

## 2. 游戏开发需要的 Skill 清单

按环节盘点。表中「检查点」是一票否决项，缺了就不算这个技能能用。

| 环节 | 需要的 Skill | 产出 | 检查点 |
| --- | --- | --- | --- |
| 策划与文档 | 设计文档起草与体检、竞品拆解 | 可执行的 spec | 数字与结论逐条核实 |
| 数值与平衡 | 数值表生成、改动回归报告 | 平衡报告 | 用真实数据回放验证 |
| 代码与工具 | 脚手架、重构、测试生成 | 可过测试的改动 | 读 diff + 测试全绿 |
| 引擎操作 | 场景搭建、批量属性、截图冒烟（走 MCP） | 编辑器内改动 | 截图比对 + 分支提交 |
| 关卡与数据 | 地图数据校验、批量关卡脚本 | 关卡草稿 | 抽几关进游戏真跑 |
| 美术管线 | 概念图、资产生成、风格锚点维护、像素化与切图 | 可进管线的资产 | 对照锚点 + 人工精修 |
| 音频 | 生成、裁剪、循环点与响度检查 | 可用片段 | 耳听循环与响度 |
| 叙事 | 设定库维护、对话树生成、一致性核对 | 对话初稿 | 一致性表逐条过 |
| 本地化 | 术语表维护、批量翻译、LQA 清单 | 译稿 | 每语言抽样精读 |
| QA | 冒烟机器人、视觉回归、崩溃聚类 | 工单 | 严重级人工复核 |
| 构建与发布 | CI 编排、版本说明、商店素材 | 可发布构建 | 真机验收 |
| 运营 | 更新日志、社区回复草稿 | 草稿 | 对外文字人工定稿 |
| 团队基建 | 上下文文件维护、提示词库、AI 使用台账 | 长期资产 | 定期复核 |

这张表不用一次配齐。先从你重复最多的两三个环节开始，跑顺再扩。

## 3. 两个示范：一个 Skill 写出来是什么样

### 3.1 截图冒烟技能

- **触发**：每次构建产出后，或一句「跑冒烟」。
- **输入**：构建产物路径、要过的关卡与路径。
- **步骤**：无头启动 → 按脚本模拟输入 → 关键节点截图 → 与基线对比 → 输出差异清单。
- **工具与权限**：引擎命令行、截图工具；只读权限，仅允许写截图目录。
- **验收**：全部截图完成对比，差异帧列成清单，留给人判定真假问题。

### 3.2 风格锚点技能

- **触发**：生成任何新资产之前。
- **步骤**：载入锚点集 → 生成 → 与最近锚点对比 → 不合格重来 → 通过后登记台账。
- **验收**：成品与锚点同风格；台账四项（工具、模型、日期、人工修改程度）齐全。

两个例子的共同点：步骤能照做、验收能执行、权限讲到具体路径。这就是 Skill 和「一段提示词」的区别。

## 4. 怎么得到这些 Skill：三条路

1. **用现成的**：代理自带的技能生态、插件与 MCP 市场先搜一轮。引擎操作、Blender、浏览器自动化都有现成实现。
2. **配置规则**：AGENTS.md 加提示词库（主册 §10），成本最低，先做这两样。
3. **自建技能包**：同一流程重复三次以上，就值得写成一个 Skill。

顺序建议：先配规则，再试现成生态，自建放第三步。规则不齐就装一堆插件，只会把混乱自动化。

## 5. 自建 Skill 的写法

一个技能包至少回答七个问题，推荐用一份固定结构的说明文件承载：

```markdown
# 技能名
## 用途         一句话：干什么活，什么时候用
## 触发条件     什么话、什么时机触发
## 前置条件     需要哪些文件、权限与工具
## 步骤         编号步骤，命令写全
## 验收标准     能自动查的写成检查；不能的写明人工项
## 权限与红线   允许写哪些路径；哪些动作必须人工确认
## 维护记录     最近复核日期、适用的引擎与模型版本
```

三条纪律：步骤要能照着做得下去（含真实命令）；验收必须是可执行的动作；红线要写具体的路径和动作，不写「注意安全」这种空话。

存放位置：跟项目走最稳。放仓库里（例如 `tools/skills/` 目录），和代码一起版本化，团队共享。

## 6. 维护与治理

- **版本绑定**：引擎、模型换代后，相关 Skill 逐条复核，改不动的先标记停用。
- **评审**：新 Skill 先小范围试用，通过再推广。
- **回归**：技能改动要走评审。一个坏技能影响的是一批产出，比没技能更贵。
- **废弃**：过时的删掉或明确标记，别留一堆还能用但没人用的僵尸技能。

## 7. 人的部分

工具会了，不代表人可以不懂。三件事推不出去：验收标准（你得会写）、审美判断（手感、风格、节奏）、责任（披露与合规）。

最小能力清单：读得懂 diff，跑得了测试，看得出数据异常，能把需求写成可验收的一句话。

一句提醒：Skill 是杠杆，判断是本金。本金不够，杠杆只会把损失放大。
