# GameDev Atlas · 制作管理手册

> **迭代第 ⑫ 轮**。定位：把"做完一款游戏"变成可管理流程的手册，覆盖立项文档、估算排期、阶段模型、范围控制、团队协作、外包管理、测试 QA、风险管理、单人开发专章、复盘方法。
> 配套：《游戏设计手册》（⑨）·《技术实现手册》（⑩）·《避坑大全》（⑥，项目管理章节）·《全平台上架手册》（⑧）· 模板库（设计文档 §9）。
> 原则：**管理是服务于"发布一个好东西"的**；流程越轻越好，但每一刀砍的功能都要有记录。

---

## 1. 立项包（项目开始前必须存在的三份文件）

| 文件 | 内容 | 篇幅 |
| --- | --- | --- |
| 一页纸（Pitch） | 概念/玩家幻想/核心循环/目标平台/受众与竞品/差异点/商业模式 | 1 页 |
| Mini GDD | + 操作、系统清单、内容规划（关卡表）、美术音频方向、技术底线 | 3-8 页 |
| 范围声明（Scope Statement） | **明确不做清单** + 成功标准（什么算"做成"）+ 里程碑草案 | 1 页 |

> 成功标准必须可验收（如"上线 Steam，好评率 ≥80%，回本"），"好玩"不是标准。

## 2. 估算与排期

### 2.1 估算方法

- **类比估算**：找一个完成过的同类功能/作品（自己的前作最准）→ 打系数（新领域 ×1.5-3）。
- **三点估算**：乐观/现实/悲观取 `(O+4M+P)/6`；游戏资产类默认取悲观值。
- **经验倍数**：内容制作（关卡/美术）常见 = 首次估算 ×2-3；联机/未知平台 ×2+。
- **缓冲**：总工期留 **30-50%** 缓冲（不是偷懒，是行业统计出来的现实）。

### 2.2 里程碑设计

| 里程碑 | 定义（可验收） | 检查 |
| --- | --- | --- |
| 原型（Prototype） | 核心循环可玩，含占位资源 | "玩具测试"通过（⑨§1） |
| 垂直切片（Vertical Slice） | 一小段达**最终质量**的完整体验 | 质量标杆成立 + 工时校准（用它重算全量工期） |
| Alpha | 所有系统齐备（功能全，内容缺） | Feature Lock：功能清单冻结 |
| Beta | 所有内容齐备（可完整通关/游玩） | Content Lock：内容冻结，只修 bug 与打磨 |
| RC / Gold | 可发布候选版 | Code Lock：只允许修阻断级 bug |

- 挂机法则：里程碑 = **能玩的构建**（Build），不是"代码写完""文档写完"。
- 每周/双周节奏：周一定目标（3 件以内）→ 周五可玩构建 + 简报（完成了什么/卡在哪/下周做什么）。

## 3. 范围控制（决定项目生死的技能）

- **优先级框架**：MoSCoW（Must/Should/Could/Won't）逐条标注；"Won't" 明确写下并公示（防复活）。
- **砍功能顺序**（从最先砍到最后砍）：外观皮肤 → 支线内容 → 附加模式（Photo Mode/无尽模式）→ 系统深度（天赋树分支）→ 内容量（关卡数/角色数）→ **核心循环相关的一切最后砍**。
- **原则**：砍掉的是功能，保住的是体验与完成度；**"做完的小游戏" > "没做完的神作"**（见⑥）。
- 新增功能审批：任何新增必须"一换一"（砍一个等量项），并记录在变更日志。

## 4. 迭代节奏与团队协作

### 4.1 小团队（2-8 人）最小流程

- 看板（HacknPlan/Codecks/飞书/Trello）：Todo / Doing / Review / Done 四列；每张卡 ≤2 天产出。
- 站会：每天 15 分钟（或异步文字版）；只回答"昨天/今天/阻塞"。
- 决策记录（ADR）：技术/设计重大决定各写 5 行（背景/选项/决定/后果），防止"集体失忆"。
- 文档纪律：单一事实来源（Notion/语雀/仓库 docs），**不在私聊里做决策**（见⑥）。

### 4.2 角色与分工（小团队合并术）

| 大厂角色 | 小团队归并到 | 要点 |
| --- | --- | --- |
| 制作人/项目经理 | 团队任一成员兼任 | 只做三件事：范围/进度/风险 |
| 策划（系统/关卡/数值） | 主设计或程序兼任 | 数值必须进表（⑨§4.1） |
| 技术美术 | 美术负责人 + 程序协作 | 资产规范与导入脚本 |
| QA | 全员轮值 | 每版本固定"破坏性测试"时段 |

### 4.3 外包管理流程

1. 需求包（参考图 + 规格表 + 验收标准 + 交付格式）→ 2. 询价与试单 → 3. 里程碑合同（分批付款）→ 4. 分批验收（草稿→终稿）→ 5. 源文件与授权归档（合规见⑦）。

- 验收标准必须**可量化**（尺寸/风格比对图/动效时长），不接受"感觉不对"式往返。

## 5. 测试与 QA

- **试玩组织**（渐进式）：自测 → 内部互测 → 定向外部（目标玩家 5-10 人）→ 公开试玩版（Demo/Next Fest，⑬）。
- **QA 计划最小集**：功能清单逐项验证 + 破坏性测试（拔线/睡眠/满内存/连点）+ 回归清单（老 bug 复测）+ 设备矩阵（⑧/⑩）。
- **Bug 分级**：

  | 级别 | 定义 | 处理 |
  | --- | --- | --- |
  | S1 阻断 | 崩溃/卡死/丢档/无法继续 | 立即修，阻断发布 |
  | S2 严重 | 功能失效但有绕行 | 发布前必修 |
  | S3 一般 | 体验问题/小错误 | 排期修 |
  | S4 轻微 | 文本/视觉瑕疵 | 有空修（进 backlog） |

- 测试记录进统一系统（看板/Excel 均可），每个 bug 附：复现步骤/环境/截图或录像。

## 6. 风险管理

- **风险登记表**（每月复盘更新）：

| 风险 | 概率 | 影响 | 预案 |
| --- | --- | --- | --- |
| 核心成员离开/生病 | 中 | 高 | 关键系统文档化；无单点知识 |
| 工期乐观（最常见的风险） | 高 | 高 | 缓冲 + 砍功能预案已就绪 |
| 引擎/平台技术坑（如某平台导出失败） | 中 | 中 | 早期技术验证（spike，见设计文档 §19 计划） |
| 审核/版号延误（国内） | 中 | 高 | 提前 6-12 个月规划（⑧）、出海备选 |
| 资金断裂（全职开发） | 中 | 极高 | 预留 6-12 个月生活费；接外包/兼职过渡 |
| 被竞品撞车/抄袭 | 低 | 中 | 速度 + 社区 + 差异化（⑦§7.5） |

- 每个风险有"触发条件"（如"切片工时超估 50%"→ 启动砍功能预案），到点即执行，不辩论。

## 7. 单人开发专章

- **时间现实检查**：每周可用工时 = 总工时 - 生活 - 正职（若有）；按每周 10h 计，一个小项目 ≈ 6-12 个月，按此定范围（一页纸直接缩小到能装下的尺寸）。
- **每周交付物**：每周结束时必须有一个"能打开看到变化"的构建，进度可见是动机的燃料。
- **防弃坑策略**：把项目拆成"多个可发布的小阶段"；每阶段有公开承诺（devlog/社区）；卡住 3 天必须换任务或求助（见⑥倦怠坑）。
- **外包选择**：美术/音乐优先外包（性价比最高的杠杆）；自己只做"核心乐趣 + 系统"。
- **心态**：完成度 > 完美度；发布时的"遗憾清单"是下一作的起点。

## 8. Game Jam 练兵（把管理能力去健身房）

- 价值：48 小时内走完"立项→范围→制作→发布"全流程；专治"永远做不完"的人。
- 策略：先定"能玩的一句话"→ 砍到最核心 → 美术/音频全用素材或 AI 辅助 → 提交前 2 小时冻结（⑧模板）。
- 参加节奏：一年 2-4 次；每个 Jam 刻意练一个弱项（叙事/关卡/手感/发布流程）。

## 9. 复盘方法（项目结束/里程碑后必做）

- **写复盘**：目标 vs 结果（数据）→ 做对了什么（可复用）→ 做错了什么（根因，不追责）→ 下次改什么（可执行项 ≤5 条）。
- **读复盘**：优先读"同类型 × 同规模"的复盘（《资源大全》§4 与 `docs/postmortems/`）；警惕幸存者偏差：失败案例更有信息量。
- 复盘存档：进 `docs/postmortems/`（模板见 `templates/postmortem.md`），成为团队资产。

## 10. 制作节奏模板（可直接抄）

| 周期 | 动作 |
| --- | --- |
| 每日 | 15 分钟同步（文字即可）；记录阻塞项 |
| 每周 | 周五：可玩构建 + 3 行简报；周一：定 ≤3 个周目标 |
| 每月 | 风险登记表复核 + 范围声明复核（有没有偷偷加东西）|
| 每里程碑 | 验收标准逐条勾 + 复盘 + 重新估算后续工期 |
| 每版本发布 | 发布检查清单（⑧§10）逐项过 |

> 一句话总结：**范围可信 × 节奏可见 × 砍得果断 = 项目能活着做完。** 剩下的交给《运营与增长手册》把它变成生意。
