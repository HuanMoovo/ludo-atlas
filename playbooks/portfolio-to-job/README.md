# Ludo Atlas · 实践手册 · 从作品集到求职

> **实践手册**。定位：把「做过的东西」整理成「招得进来的证据」：作品集怎么组、放在哪，简历怎么写、往哪投，测试题与面试怎么打，没回音时怎么继续。
> 配套：《独立开发者深度谱》（别人的入行与转型路径）·《人物与厂商谱》（先认识行业里的人）·《游戏简史》（面试聊行业脉络的底料）·《避坑大全》（全流程坑位对照）。

---

## 1. 适用场景与目标

适用：

- 你手上有 1-3 个能运行的项目，准备进入行业求职（程序、设计、美术、音频、制作、QA、发行、运营任一线）。
- 你正在走《学习路径》的「求职」路线，从技能训练切换到作品集与投递阶段。
- 你投过一批简历但回音寥寥，想知道卡在哪一环。

不适用：还没做出能运行的作品，先完成[第一个游戏](../../docs/start/first-game.md)；目标是独立发布，转《独立开发生存手册》。

目标（1-3 个月）：

1. 把已有项目整理成陌生人能独立看懂、能当场验证的求职材料（作品集、载体、简历）。
2. 完成至少两轮完整投递循环：投递 → 测试题 → 面试 → 反馈。
3. 拿到 offer，或者拿到一份「差距在哪、下一步补什么」的清单。

三条原则：

1. **求职是链路，先修最弱一环**：作品集、简历、投递、测试、面试，任何一环断掉，后面全线归零；复盘先问「这次卡在哪一环」。
2. **证据优先，形容词作废**：招聘方只会打开链接、点开构建、追问细节；没被验证的「熟悉」「精通」等于没写。
3. **反馈循环**：每批投递都有台账与复盘；沉默也是数据，用来修正下一批，不用来打击自己。

时间预算：每天 2-4 小时，外加每周一个集中日；投递本身很便宜，别用「再准备准备」拖延它。

## 2. 全景流程

主循环写成动词链：

`拆岗位 → 补证据 → 打磨作品 → 投递 → 测试题 → 面试 → 写复盘 → 补短板`

循环到拿到 offer 或确认差距；正常情况下两到四轮。

| 阶段 | 产出 | 时长 |
| --- | --- | --- |
| 定向与对标 | 岗位清单（冲刺、匹配、保底分档）+ 20 份岗位描述的高频技能表 | 1-2 周 |
| 作品集成军 | 三件套（完整、炫技、对口）+ 每个作品一页说明 | 2-6 周，与投递滚动 |
| 载体与简历就位 | itch.io 条目、代码仓库整理、一页简历、作品集落点 | 1-2 周 |
| 投递与测试 | 投递台账 + 测试题交付包 | 每批 2-4 周 |
| 面试与复盘 | 复盘话术、答题记录、差距清单 | 每轮 1-3 周 |
| 迭代 | 按差距清单回修作品与技能，进下一批 | 循环进行 |

全流程从开始整理到拿到明确结果，常见 2-4 个月。时间主要花在打磨作品与等待反馈上，投递动作本身只占一小部分。

## 3. 分步执行

### 3.1 作品集三件套

三件套各自回答一个问题：能不能做完、能力上限在哪、跟岗位匹配吗。数量纪律：三个打磨过的，胜过十个半成品。

| 作品 | 回答的问题 | 合格线（可观察） |
| --- | --- | --- |
| 完整作品 | 你能把东西做完吗 | 陌生人 10 分钟内能自己玩起来；有开头有结尾；有发布形态（可下载或网页可玩） |
| 技术炫技 | 你的能力上限在哪 | 一个可交互演示加一页技术说明：难点、做法、取舍、验证方式 |
| 岗位对口 | 你跟这个岗位匹配吗 | 招聘方拿着岗位描述，能逐条在你的作品里找到证据 |

按岗位线微调：

- 程序岗：对口件选目标方向（玩法、工具、渲染、服务端）的系统案例；代码仓库必配。
- 设计岗：对口件用「拆解文档 + 可玩关卡或测试作品」，展示从判断到落地的全过程。
- 美术岗：对口件是一套主题统一的资产（角色、场景、界面同风格），附过程稿；音频岗用一段能听出实现思路的音频实现案例，而不是纯素材拼贴。
- 制作、QA、运营岗：对口件用进度管理案例、测试报告、内容策划或数据复盘。

说明文档底线（每个作品一页）：这是什么、怎么玩或怎么看、你负责哪部分、用了什么（工具与第三方资源）、开发周期与已知问题。教程跟做或素材借用要明说并注明来源：明说只减一点分，藏着被扒出来才归零。每个作品都要经得起讲 15 分钟，讲不满的先补文档或先砍掉。

### 3.2 展示载体：三个渠道的取舍

| 载体 | 强项 | 弱项 | 用法 |
| --- | --- | --- | --- |
| itch.io | 免费即开；可网页直接玩；独立圈认可度高 | 招聘方不常主动逛 | 所有可玩作品的默认入口；页面写清玩法、时长、操作 |
| 代码仓库（GitHub 等托管平台） | 展示代码质量、提交记录与工程习惯 | 美术、设计岗一般没人看；仓库乱是减分项 | 程序与技术岗必备；README 三件事：这是什么、怎么跑起来、我的分工 |
| 个人站 | 一页让招聘方 30 秒看完你是谁、会什么、作品在哪 | 有维护成本；几乎没有自然流量 | 简历上的唯一落点；点进去直达作品与联系方式 |
| 过程记录（视频、日志） | 展示过程与思考；美术、动画、特效岗刚需 | 只有视频看不到可玩性 | 作补充证据，不替代可玩构建 |

取舍原则：

- 起步优先级：可玩构建 → 代码仓库（看岗位） → 一页个人站 → 过程记录。
- 招聘方打开你的链接只有一次机会：第一屏要能玩到或看懂；需要注册、下载解压、翻三页说明才能访问的入口，直接换掉；每月点一遍所有链接，失效链接比没有链接更减分。
- 个人站极简即可：三段话（我是谁、我会什么、作品在哪）加 3-5 个链接，半天做完，别拿它当作品。
- 代码仓库的卫生：提交记录持续、命名整洁、不传构建产物与密钥；招聘方看提交记录就是在看工程习惯。

### 3.3 简历：句式与量化

一页纸；上三分之一决定去留：姓名、求职方向、联系方式、作品集链接。

句式固定为「动词开头 + 对象 + 方法 + 结果」。对照改法：

| 弱写法 | 强写法 |
| --- | --- |
| 负责优化了游戏性能 | 把主场景帧率从 32 提到 60：定位到绘制批次过密，用图集合并与遮挡剔除解决 |
| 参与多人联机模块开发 | 独立实现 4 人房间的状态同步：弱网 200ms 下角色位置误差控制在半个身位内 |
| 熟悉引擎与常见工具 | 用引擎完成 3 个完整项目并发布：其中 2 个收到陌生玩家的通关反馈 |

量化素材：

- 性能与规模：帧率、内存、加载时间、包体大小、绘制次数；系统数、关卡数、资产套数、文档页数。
- 验证与事实：测试人数、通关率、反馈条数、活动入围记录；发布了、有人在玩、被某次活动收录、源码被陌生人拿到。

没有数字就用可验证事实，不编数字。技能表按「熟练、用过、了解」三级如实填写，别堆「精通」；岗位描述里出现的高频词，至少有一个使用场景能当场讲。

定制：每投一个岗位，花 10 分钟做关键词对齐（把岗位描述里反复出现的 5 个词挪到简历显眼处）；同一份简历海投是反馈率的头号杀手。

投递信保持三句话：

> 您好，应聘某岗位。简历与作品集链接见下。与岗位最相关的两件事：把某系统性能提升了一倍；完整发布过一个带关卡编辑器的项目。期待进一步沟通。

### 3.4 投递策略与测试题应对

投递策略：

- 分档建池：冲刺档、匹配档、保底档各约占三分之一；匹配档指岗位描述里的技能你覆盖七成以上。
- 每批 8-15 个岗位，周期 2-4 周；用台账记录：岗位、渠道、投递日、状态、反馈。作品集做到 80 分就投第一轮，剩下 20 分补在哪，反馈会告诉你，闭门准备永远准备不完。
- 渠道组合：招聘平台、公司官方渠道、行业社群与内推、开发活动与展会。内推的用法是把作品集递到一个具体的人手里，等作品集就位再用。

测试题应对：

- 先问清四件事：时间预算、交付范围、允许的素材与工具、能否公开；再选最小可完整交付的切口：先保证能跑加有说明，再谈加分项，把时间分配写进说明，招聘方看的正是取舍。问清楚不减分，交付一个超范围的大东西才减分。
- 交付包固定三件：可直接运行的构建、源码、一页说明（题目理解、做法、取舍、已知问题、下一步）。
- 测试题内容未经允许不公开、不复用；节点前主动同步进度。结果无论好坏都留一份复盘：测试题是行业最真实的技能校准。

### 3.5 面试准备：复盘话术与答不上来

项目复盘五段（每段一句话，3 分钟版）：背景（给谁做的、多大范围）、目标（要解决什么）、做法（关键决策与取舍）、结果（数字或可验证事实）、复盘（重做会改什么）。再准备一个 15 分钟版，把每段展开成「为什么」。

高频追问与预备答案：

| 追问 | 预备什么 |
| --- | --- |
| 为什么这么做？ | 每个关键选择的两三个备选方案与排除理由 |
| 哪部分是你做的？ | 如实切分分工；把队友功劳算给队友，追问两轮必露馅 |
| 重做会改什么？ | 具体到架构、流程或范围；「没什么可改」是减分项 |
| 数据怎么来的？ | 数字的出处与口径，随口能报 |

答不上来时的三步：

1. 承认边界：这块我没做过，或者不确定。
2. 给相邻经验：我做过的某件事与之同源，我的推断是……
3. 给行动方案：如果上手，我会先做哪一步来验证。

不装懂、不沉默、不硬编；面试官测的是未知面前你怎么工作。行为面试准备三个一分钟故事（团队冲突、失败、赶工），用真实项目做背景，主语用「我」不用「我们」。反问环节备三问：项目现在什么阶段、团队怎么分工与验收、入职第一个月期望交付什么；第三个问题能反向验证岗位的真实要求。

每场面完 24 小时内写记录：被追问最多的点、答砸的点、下轮要补的点。同一个问题挂了三次，就不是运气问题。

### 3.6 持续经营：开发日志与社区信号

- 开发日志：每周或每两周一篇，写「做了什么、卡在哪、怎么解决、下一步」；发在自己的主阵地，同步到作品集页面。投递低谷期正是积累信号的时间；每轮测试题与面试的脱敏心得，就是下一篇日志。
- 过程即证据：招聘方会用搜索验证简历上的经历；有公开记录的项目，可信度与记忆点都更高。连续八周以上的记录，本身就是一份过程作品集。
- 社区信号：在研究或开发社区留下可查的正面记录（回答问题、参加开发活动、发测试版本收集反馈）；持续在场的陌生人，比突然出现的求职者更容易被想起与内推。
- 纪律与时间盒：不吹牛、不贬低他人、不泄露面试方信息；公开账号都假设未来的面试官会看到。每周投 2-4 小时在这里，超过了就是在挤开发时间。

## 4. 验收清单

| 检查项 | 通过标准 |
| --- | --- |
| 三件套 | 齐备且分属三种角色；每件都有可点开的入口 |
| 说明文档 | 每个作品一页，四问都有答案（是什么、怎么玩、我做了什么、用了什么） |
| 载体 | 第一屏能玩到或看懂；无失效链接；手机打开不崩 |
| 简历 | 一页；每条经历是「动词 + 方法 + 结果」；链接可直达 |
| 投递台账 | 每批 8-15 个岗位；渠道、时间、状态、反馈都有记录 |
| 测试题 | 按时交付；构建、源码、一页说明三件齐全 |
| 面试 | 3 分钟与 15 分钟两版复盘；三类行为故事各一 |
| 持续经营 | 最近 8 周有公开更新；搜索自己的名字能查到正面记录 |
| 复盘循环 | 每轮结束有一页差距清单与下一步动作 |

清单全打勾仍拿不到面试，问题多半在岗位匹配或渠道，回到 §3.2 与 §3.4 重调，而不是继续加作品。

## 5. 常见坑

1. **只有教程复刻**：三个作品全是跟着教程敲的，一问「哪里是你自己决定的」就露馅。至少留一个从选题到发布全程自己决策的作品；炫技件可以是复刻变体，但要能说清你改了什么、为什么。
2. **作品无说明文档**：招聘方不会花二十分钟猜你的项目。没有一页说明，作品等于不存在；先写「怎么玩、我负责什么」，再补技术细节。
3. **只投大厂**：目标池太窄，流程长、反馈慢，容易在等待里停摆。按冲刺、匹配、保底三档投，先让一轮循环跑起来。
4. **无反馈就停**：沉默是常态（流程长、岗位撤销、筛选偏好），把它当数据不当判决；每批结束复盘作品、简历、匹配三个变量。
5. **作品集只堆数量**：十个半成品不如三个讲得透的；每个都懂一点、没有一个能讲 15 分钟，是最常见的减分项。
6. **简历写成职责说明书**：「负责了某模块」没有信息量；换成动词、方法、结果，没有数字就写可验证事实。
7. **测试题做成炫技大项目**：超时或半成品等于负分；小切口做完整，把取舍写进说明。
8. **作品与岗位错位**：投服务端却全是单机小作品，投系统策划却只有美术练习；对着岗位描述的高频词逐条补证据。
9. **面试装懂**：硬编答案一旦被追问就是诚信问题；用「承认边界、相邻经验、行动方案」三步接住。
10. **经营中断**：求职期停更、社群消失，面试官一搜最近一条是半年前；每周两小时维护公开信号就够。
